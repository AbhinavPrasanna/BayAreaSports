# Bayline production operations

This runbook describes the production path. Commands and files alone are not proof of a successful deployment: record actual image digests, restore output, restart counters and HTTPS checks in `DEPLOYMENT.md` as they complete. Never put credentials in this repository, a build argument, a release archive or terminal output.

## Design and cost limits

One Ubuntu 24.04 Lightsail `medium_3_0` server in `us-west-2` costs $24/month (2 vCPU, 4 GiB, 80 GB disk). Only Caddy publishes ports 80/443. PostgreSQL is attached solely to an internal Docker network; neither 5432 nor the web server's 3000 is published. Web and worker are separate non-root containers, with restart policies, resource limits, read-only filesystems and file-backed secrets. The worker retains its own schedule and persistent provider throttle across restarts.

Plan $30–40/month for Bayline under modest MVP traffic, excluding a separately chosen annual domain registration. Allocation: $24 host, $1 backup storage plan (5 GB included; measured overage possible), about $1 for small ECR/build-artifact storage, $2 for occasional CodeBuild runs, up to $3 for HTTPS health checks/alarms/SNS/DNS, and $9 contingency. BALLDONTLIE remains on the free tier. No load balancer, NAT gateway, managed RDS, paid sports plan, reserved build fleet or CDN is needed. Traffic beyond the instance/bucket allowances, excessive build runs, retained images, storage growth and domain charges can raise costs.

Reference pricing: [Lightsail bundles](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-bundles.html), [Lightsail pricing](https://aws.amazon.com/lightsail/pricing/), [CodeBuild pricing](https://aws.amazon.com/codebuild/pricing/), [Route 53 pricing](https://aws.amazon.com/route53/pricing/). Do not rely on promotional credits to meet the budget.

The initial $100 account-wide safety budget sends actual-spend alerts at 50%, 80% and 100%, plus a forecast alert at 100%, to the user's chosen address. The user's $100 limit applies to Bayline, so existing unrelated projects are outside its cost allocation and must not be modified. AWS budgets report with a delay and **do not stop spending**. Activate the `Project=Bayline` cost-allocation tag when AWS makes it available, then add a project-scoped budget. Review project costs and image/storage size monthly; leave room for domain renewal and taxes.

## Provision and build

1. Refresh the operator's AWS SSO session. Never copy SSO/access keys to the host.
2. Generate the regional template: `node deploy/aws/template.mjs /absolute/path/stack.json`. Create/update `bayline-mvp-prod` in `us-west-2` with `AlertEmail`, the operator's public IPv4 `/32` as `AdminCidr`, and `InstanceSuffix=01`. The template uses Ubuntu packages for Docker and downloads AWS CLI v2 from AWS. It creates the $100 budget before starting the instance. Retained buckets, repositories, static IP and instance deliberately survive stack deletion/replacement. Stack termination protection is enabled by the deployment command; remove unused retained resources explicitly only after verifying recovery.
3. Verify cloud-init completed (`/opt/bayline/host-ready`), Docker/Compose/CLI versions, the private backup bucket's instance access, and IMDSv2. Restrict SSH to the operator's `/32`. Update that rule deliberately if the operator IP changes. Do not change application ports to debug SSH.
4. Package a clean, secret-scanned Git commit with `git archive --format=zip`. Upload it to the stack source bucket at `source/source.zip`. Start one CodeBuild run with `IMAGE_TAG` set to that commit. Builds run tests/type checking and produce separate ECR `web` and `worker` images. No build runs on the Lightsail host. Build concurrency is one with a 20-minute timeout.
5. Record the ECR image digests and source commit. Pull PostgreSQL 17 and Caddy release images and record their verified digest references too. Deploy `repository@sha256:...` references; never use a mutable app tag in production.
6. Connect using short-lived credentials from `lightsail get-instance-access-details`. `aws/remote.mjs` writes temporary credentials only to an explicitly supplied ignored directory. It uses AWS host keys when returned; if the fresh Ubuntu instance omits them, it pins the first SSH contact and strictly checks subsequent connections. Obtain an independently trusted host fingerprint before initial connection in environments requiring protection against first-contact interception. Do not accept a later key mismatch without investigating.
7. Copy only the deployment directory to `/opt/bayline/deploy` as root, excluding secrets, environment files, Python caches and evidence. The provider key goes separately through SSH stdin to `install-secrets.py`; this script generates a new random database password on a new server and preserves an existing one. Parent secret directory mode is 0700/root; files are 0444 so the specific mounted files are readable by differing container UIDs. Host users cannot traverse that parent directory. Docker administrators remain privileged.
8. Create root-only `production.env` from the example using the actual image digests/bucket/region. Before DNS is ready, use `APP_DOMAIN=pending.invalid` and leave `COMPOSE_PROFILES` empty. The `public` Caddy profile stays off. Authenticate to ECR using a short-lived token over stdin, pull all release images, then log out. Reboots use cached images (`--pull never`). Recovery pulls require a new operator token.
9. Run `docker compose --env-file production.env -f compose.production.yaml config --quiet` without displaying expanded configuration. Start `db`, `migrate`, `web`, and `worker`. Verify migration 003 and at least one stored game; allow the provider's request spacing. Do not run a second worker against a different database with the same key while testing.

## Before public launch

All host commands run from `/opt/bayline/deploy` as root. Backups use the host's Lightsail bucket resource access through IMDSv2; there is no long-lived AWS credential on the server. The app containers must not receive that access. Keep IMDS hop limit at 1 once provisioning completes, and verify host backup access still works.

1. Run `python3 ops.py backup`. It writes a canary, creates a custom-format PostgreSQL dump, uploads to the private off-server bucket, downloads it again and verifies SHA-256. A manifest is published last to identify completed backups. Dump size above 200 MiB fails for a cost review. Only after verification does the live database record a successful backup.
2. Run `python3 ops.py restore`. It downloads a completed off-server backup, verifies SHA-256 and restores into a NEW `bayline_restore_YYYYMMDDHHMMSS` database in a single transaction. It checks the canary, three enabled teams, at least three migrations and nonempty games, then analyzes the restored database. It does not drop or overwrite any database. Keep this drill database until evidence is reviewed; old drill databases consume disk and should be removed individually after review.
3. Run `python3 ops.py restart-proof` and record its output. The root operator kills the inspected process for web, worker and PostgreSQL in turn; Docker must increase each container's restart count, recover health and retain data/canary. A web crash must leave the worker start time unchanged. This is different from `docker stop`, which intentionally suppresses a restart policy. Run only when a brief controlled interruption is appropriate.
4. Install the `systemd/` units into `/etc/systemd/system`, run `systemctl daemon-reload`, and enable/start `bayline.service`, `bayline-backup.timer`, `bayline-restore.timer` and `bayline-watchdog.timer`. Backups run every six hours; restoration is tested monthly; a two-minute watchdog restarts running containers whose health check becomes unhealthy. Journald is limited to 100 MB, and each container log to three 10 MB files. Verify timers with `systemctl list-timers 'bayline-*'`.
5. Reboot the instance. After it returns, verify the app and worker are healthy, the data/canary persist, and the scheduled timers are active. The single host can have a brief outage; this setup does not provide high availability or promise zero downtime.
6. Register the user's chosen domain through the normal registrar flow, or use a domain already owned. Create its DNS A record pointing to the attached static IP; remove stale AAAA records unless IPv6 is deliberately configured. Confirm authoritative/public resolution. A new domain purchase requires the user's selection and registrar contact/terms steps.
7. Set the real `APP_DOMAIN` and `ACME_EMAIL`, enable `COMPOSE_PROFILES=public`, and start Caddy. Verify a publicly trusted TLS certificate, HTTP→HTTPS redirect, successful `/api/health`, `/api/ready`, `/api/teams` and schedule/detail responses, and that 3000/5432 are unreachable externally. Test the interface in a phone viewport. Do not bypass certificate warnings.
8. Generate `aws/monitoring.mjs` and deploy the monitor stack in **us-east-1** (Route 53 health metrics are published there) with the domain and alert email. It checks `/api/ready` over HTTPS every 30 seconds, then alarms on two unhealthy minutes. Confirm the SNS email subscription. Test notification delivery with a controlled outage and recovery; an unconfirmed subscription is not working monitoring. Route 53 HTTPS checks are uptime checks, not a certificate-expiry validator; validate public TLS independently at release and renewal.

## Ongoing checks

`/api/health` checks web/database reachability. `/api/ready` additionally requires a worker heartbeat within three minutes, each free feed checked within ten minutes, a verified backup within eight hours, and a successful restore drill within 35 days. A stale feed or backup produces 503 so the independent external monitor also detects broken ingestion or recovery readiness while the UI still shows cached games. These routes expose only booleans/status.

Inspect bounded logs with `journalctl -u bayline-backup -n 30` and `docker compose --env-file production.env -f compose.production.yaml logs --tail 50 worker`. Avoid dumping container environments, the secret directory, expanded Compose configuration or the whole Docker inspect object. Verify disk free space before each release and keep at least 10 GB available. Never use `docker compose down --volumes` in normal operations.

Backups retain 35 days. Cleanup deletes only app-shaped object versions under `postgres/` older than 35 days, after at least two completed backups exist. Access is bucket-private and encrypted by Lightsail at rest and in transit. This covers **server loss**, not AWS-account compromise; instance resource access is full bucket access, not an immutable or cross-account backup. AWS credentials/account protection remains essential.

## Recovery from total server loss

Target RPO: at most six hours plus backup execution time. Target RTO: one to two hours after operator access is available. These are targets until timed drills establish measured results. Recovery does not depend on the failed server's disk, Docker volumes or saved ECR login.

1. Refresh AWS SSO, obtain the latest Git release and recorded image digests, and confirm the private backup manifests are accessible. Fence the old server so it cannot resume its worker. Do not delete any source/bucket/repository/static IP while recovering.
2. Provision a replacement Ubuntu 24.04 `$24` bundle in the same region using the infrastructure template with a new instance suffix. A replacement incurs overlapping hourly charges until the old instance is explicitly retired; budget for that short overlap. Retain and reattach the original static IP, and attach the replacement to the retained private backup bucket. A retained old instance is not automatically deleted by CloudFormation.
3. Install Docker/Compose/AWS CLI, deployment files, units and the recorded image digests. Reconfigure secrets through stdin. The database password can be freshly generated; the dump uses `--no-owner --no-acl`. Recover the provider key from the user's original encrypted/secret-manager copy. Never depend on the lost server as the only key copy.
4. Pull the recorded images using a fresh ECR token. Start **only db** on the empty replacement. Run `python3 ops.py restore --no-record --key postgres/EXACT_COMPLETED_MANIFEST.json`. This restores to the isolated timestamped database and verifies its canary/data, without requiring a schema in the newly created live database.
5. Stop all app/worker/migration processes before promotion. Confirm the newly created `bayline` database has **zero public application tables**. Preserve it by renaming it to `bayline_empty_TIMESTAMP`; then rename the verified `bayline_restore_TIMESTAMP` to `bayline`. Use `psql` connected to `postgres` and validated SQL identifiers; terminate only connections to these two named databases as needed. Never drop/overwrite an existing populated live database. If the target is not empty, stop and investigate before promotion.
6. Run the image's migrations against the restored live database, start web and exactly one worker, and verify stored schedules, a fresh heartbeat and provider checks. Take a fresh off-server backup and run the isolated restore drill again. Re-enable the timers/watchdog.
7. Reattach the static IP (or update DNS if deliberately changing it), start Caddy, verify trusted HTTPS and readiness, and confirm the external monitor returns OK. Reboot once and recheck services/data/timers. Record elapsed recovery time and the source backup timestamp to establish actual RTO/RPO.
8. Retire only the explicitly identified old instance and obsolete test databases after recovery evidence is reviewed. Do not remove the retained off-server backups or release images needed to recover again.

## Release rollback

Take and verify a backup first. Record current image digests and pin the prior compatible web/worker digests in `production.env`, pull them using a fresh ECR token if absent, and recreate only the relevant services. Do not automatically reverse database migrations. New migrations must remain backward-compatible with the prior app release or have a separately tested restore/promotion plan. Check readiness and monitor state after rollback.
