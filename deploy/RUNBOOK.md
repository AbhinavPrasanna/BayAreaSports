Commands and files alone are not proof of a successful deployment: record actual image digests, restore output, restart counters and HTTPS checks in `DEPLOYMENT.md` as they complete. Never put credentials in this repository, a build argument, a release archive or terminal output.

## Design and cost limits

CodeBuild uses `aws/codebuild/standard:7.0`. Its host runtimes are explicitly selected in `deploy/buildspec.yml`: Node.js 24 for the Compose validator and Python 3.12 for operations tests. Runtime version commands record the selections in build logs. Application compilation, dependency installation and runtime tests run separately inside the Dockerfile's Node 24 Alpine stages. AWS curated-image default changes affect the build host, not already-running digest-pinned production containers. These selections take effect when a build uses the updated source archive; they do not require restarting or redeploying the live app. After changing them, validate the YAML and run the host checks in CodeBuild before claiming cloud validation.

Automatic highlight discovery requires migration **005**, the matching web/worker images, and an optional `secrets/youtube-key` file mounted only into the worker. Create an empty file under the root-only secret directory (mode 0444) for a deployment without a key; discovery logs `enabled:false`. See [YOUTUBE-SETUP.md](../YOUTUBE-SETUP.md) for secure activation and source/retention rules. Persisted schedules, quota counters and cached video rows are included in database backups. Reinstall the YouTube key after a server restore; an IP-restricted key must permit the replacement server's outbound IP. Automatic rows expire from public reads after 28 days, including after restoration. The prior web/worker images tolerate migration 005, so roll back images/Compose without dropping either new table. Score-readiness monitoring does not monitor highlight discovery; inspect its bounded worker events/state separately.

One Ubuntu 24.04 Lightsail `medium_3_0` server in `us-west-2` costs $24/month (2 vCPU, 4 GiB, 80 GB disk). Only Caddy publishes ports 80/443. PostgreSQL is attached solely to an internal Docker network; neither 5432 nor the web server's 3000 is published. Web and worker are separate non-root containers, with restart policies, resource limits, read-only filesystems and file-backed secrets. The worker retains its own schedule and persistent provider throttle across restarts.

Plan $30–40/month in AWS costs for Bayline under modest MVP traffic, excluding annual domain registration and sports data subscriptions. Allocation: $24 host, $1 backup storage plan (5 GB included; measured overage possible), about $1 for small ECR/build-artifact storage, $2 for occasional CodeBuild runs, up to $3 for Lambda monitoring/alarms/SNS/DNS, and $9 contingency. The owner separately purchased NBA/NFL access; player-stat feeds are enabled only for those sports. The minimum monthly ALL-STAR data fees add $19.98; higher purchased tiers change that total. No additional AWS service is needed for player statistics. No load balancer, NAT gateway, managed RDS, reserved build fleet or CDN is needed. Traffic beyond the instance/bucket allowances, excessive build runs, retained images, storage growth and domain charges can raise costs.

Reference pricing: [Lightsail bundles](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-bundles.html), [Lightsail pricing](https://aws.amazon.com/lightsail/pricing/), [CodeBuild pricing](https://aws.amazon.com/codebuild/pricing/), [Lambda pricing](https://aws.amazon.com/lambda/pricing/), [CloudWatch pricing](https://aws.amazon.com/cloudwatch/pricing/). Do not rely on promotional credits to meet the budget.

The $100 budget sends actual-spend alerts at 50%, 80% and 100%, plus a forecast alert at 100%, to the user's chosen address. It conservatively covers Lightsail, ECR, CodeBuild, Lambda, CloudWatch, SNS, S3 and EventBridge in `us-west-2`, excluding unrelated RDS/EC2/network charges. Other projects using those same services in Oregon will also count; no unrelated resources are modified. This service/region filter works immediately while the new `Project=Bayline` billing tag is not yet indexed. AWS budgets report with a delay and **do not stop spending**. Activate the tag once available to refine attribution later. Review project costs and image/storage size monthly; leave room for domain renewal, taxes and charges outside this regional service filter.

## Provision and build

1. Refresh the operator's AWS SSO session. Never copy SSO/access keys to the host.
2. Generate the regional template: `node deploy/aws/template.mjs /absolute/path/stack.json`. Create/update `bayline-mvp-prod` in `us-west-2` with `AlertEmail`, the operator's public IPv4 `/32` as `AdminCidr`, and `InstanceSuffix=01`. The template uses Ubuntu packages for Docker and downloads AWS CLI v2 from AWS. It creates the $100 budget before starting the instance. Retained buckets, repositories, static IP and instance deliberately survive stack deletion/replacement. Stack termination protection is enabled by the deployment command; remove unused retained resources explicitly only after verifying recovery.
3. Verify cloud-init completed (`/opt/bayline/host-ready`), Docker/Compose/CLI versions, the private backup bucket's instance access, and IMDSv2. From the operator CLI run `aws lightsail update-instance-metadata-options --instance-name INSTANCE --http-tokens required --http-put-response-hop-limit 1 --region us-west-2`; verify host bucket access still works. This stops bridged app containers retrieving the host's bucket credentials. Restrict SSH to the operator's `/32`. Update that rule deliberately if the operator IP changes. Do not change application ports to debug SSH.
4. Package a clean, secret-scanned Git commit with `git archive --format=zip`. Upload it to the stack source bucket at `source/source.zip`. Start one CodeBuild run with `IMAGE_TAG` set to that commit. Builds run tests/type checking and produce separate ECR `web` and `worker` images. No build runs on the Lightsail host. Build concurrency is one with a 20-minute timeout.
5. Record the ECR image digests and source commit. Pull PostgreSQL 17 and Caddy release images and record their verified digest references too. Deploy `repository@sha256:...` references; never use a mutable app tag in production.
6. Connect using short-lived credentials from `lightsail get-instance-access-details`. `aws/remote.mjs` writes temporary credentials only to an explicitly supplied ignored directory. It uses AWS host keys when returned; if the fresh Ubuntu instance omits them, it pins the first SSH contact and strictly checks subsequent connections. Obtain an independently trusted host fingerprint before initial connection in environments requiring protection against first-contact interception. Do not accept a later key mismatch without investigating.
7. Copy only the deployment directory to `/opt/bayline/deploy` as root, excluding secrets, environment files, Python caches and evidence. The provider key goes separately through SSH stdin to `install-secrets.py`; this script generates a new random database password on a new server and preserves an existing one. Parent secret directory mode is 0700/root; files are 0444 so the specific mounted files are readable by differing container UIDs. Host users cannot traverse that parent directory. Docker administrators remain privileged.
8. Create root-only `production.env` from the example using the actual image digests/bucket/region. Before DNS is ready, use `APP_DOMAIN=pending.invalid` and leave `COMPOSE_PROFILES` empty. The `public` Caddy profile stays off. Authenticate to ECR using a short-lived token over stdin, pull all release images, then log out. Reboots use cached images (`--pull never`). Recovery pulls require a new operator token.
9. Run `docker compose --env-file production.env -f compose.production.yaml config --quiet` without displaying expanded configuration. Start `db`, `migrate`, `web`, and `worker`. Verify migration 003 and at least one stored game; allow the provider's request spacing. Do not run a second worker against a different database with the same key while testing.

## Before public launch

All host commands run from `/opt/bayline/deploy` as root. Backups use the host's Lightsail bucket resource access through IMDSv2; there is no long-lived AWS credential on the server. The app containers must not receive that access. Keep IMDS hop limit at 1 once provisioning completes, and verify host backup access still works.

1. Run `python3 ops.py backup`. It writes a canary, creates a custom-format PostgreSQL dump, uploads to the private off-server bucket, downloads it again and verifies SHA-256. A manifest is published last to identify completed backups. Dump size above 200 MiB fails for a cost review. Only after verification does the live database record a successful backup.
2. Run `python3 ops.py restore`. It downloads a completed off-server backup, verifies SHA-256 and restores into a NEW `bayline_restore_YYYYMMDDHHMMSS` database in a single transaction. It checks the canary, three enabled teams, at least three migrations and nonempty games, then analyzes the restored database. It does not drop or overwrite any database. Keep this drill database until evidence is reviewed; old drill databases consume disk and should be removed individually after review.
3. Run `python3 ops.py restart-proof` and record its output. The root operator kills the inspected process for web, worker and PostgreSQL in turn; Docker must increase each container's restart count, recover health and retain data/canary. A web crash must leave the worker start time unchanged. This is different from `docker stop`, which intentionally suppresses a restart policy. Run only when a brief controlled interruption is appropriate.
4. Install the `systemd/` units into `/etc/systemd/system`, run `systemctl daemon-reload`, and enable/start `bayline.service`, `bayline-backup.timer`, `bayline-restore.timer` and `bayline-watchdog.timer`. Backups run every six hours; restoration is tested monthly; a two-minute watchdog restarts running containers whose health check becomes unhealthy. Journald is limited to 100 MB, and each container log to three 10 MB files. Verify timers with `systemctl list-timers 'bayline-*'`.
5. Reboot the instance. After it returns, verify the app and worker are healthy, the data/canary persist, and the scheduled timers are active. The single host can have a brief outage; this setup does not provide high availability or promise zero downtime.
6. Domain option: register the user's chosen domain through the normal registrar flow, or use a domain already owned. Create its DNS A record pointing to the attached static IP; remove stale AAAA records unless IPv6 is deliberately configured. Confirm authoritative/public resolution. A new purchase requires the user's selection and registrar contact/terms steps. Alternatively launch using the **static IP**: Caddy 2.11.7 with `Caddyfile.ip` explicitly requests a publicly trusted Let's Encrypt `shortlived` certificate and sets default SNI for IP clients. These certificates last about six days and renew automatically. This avoids a domain purchase while the user chooses a name; it is not a self-signed certificate. See [Let's Encrypt IP certificate support](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability).
7. Set `APP_DOMAIN` to the domain or static IP, `CADDY_CONFIG=./Caddyfile` or `./Caddyfile.ip` respectively, and the correct `ACME_EMAIL`. Enable `COMPOSE_PROFILES=public` and start Caddy. Verify a publicly trusted TLS certificate, HTTP→HTTPS redirect, successful `/api/health`, `/api/ready`, `/api/teams` and schedule/detail responses, and that 3000/5432 are unreachable externally. Test the interface in a phone viewport. Do not bypass certificate warnings. Switching to a custom domain later requires its DNS, the domain Caddyfile and the monitor's Endpoint parameter; it does not require changing the database. Browser-local saved preferences are scoped to each origin.
8. Generate `aws/monitoring.mjs` and deploy the monitor stack in `us-west-2` with `Endpoint` (domain or IP without a scheme) and `AlertEmail`. Its independent Lambda checks `/api/ready` every minute, validates TLS trust/identity and requires over two days of certificate validity. A fresh TLS connection avoids missing certificate details on resumed sessions. CloudWatch alarms on two failed minutes or missing monitor data, and sends both ALARM and OK notifications through SNS. Confirm the email subscription. Test a controlled outage with an automatic restart and a separately scheduled failsafe restart; verify actual alarm transitions and successful SNS actions. An unconfirmed subscription is not working monitoring.

## Ongoing checks

Player status requires migration 008 and the matching web/worker release. `PLAYER_STATUS_LEAGUES` defaults empty; validate NBA/NFL active-player and injury endpoints before setting it to `nba,nfl`. WNBA status access remains disabled. Reports are current snapshots, not historical game-day injury data. Recovery must restore `team_player_status`/`player_status_gate`, complete report payloads and check times, retain the worker-only key, and verify only intended teams are enabled. This optional cache is monitored separately from score readiness. Use the owner-session publisher and checks in [PLAYER-STATUS.md](../PLAYER-STATUS.md); it performs a verified backup and isolated restore. Never reverse the additive migration during image rollback.

Advanced game details require migration 007. NBA/NFL quarter snapshots are stored on `games.line_score` by normal score ingestion. Current production uses `PLAYER_STATS_LEAGUES=nba,nfl` after successful entitlement and payload validation; only NBA/NFL `player_stats_access.enabled` rows must be true. The worker caches complete game-specific player snapshots and retains them on refresh failure. Examples/defaults remain empty for installations without paid access. To disable, empty that setting and recreate only worker; do not delete cached rows. WNBA quarter scores are absent from its free games response, and WNBA Advanced details remains hidden. After restore, preserve the production setting and verify seven migrations, stored quarter/player snapshots and the intended access rows alongside records/media and the recovery canary. See [ADVANCED-DETAILS.md](../ADVANCED-DETAILS.md). Score readiness does not monitor optional player-stat freshness; inspect `game_player_stats.error_code`, `checked_at` and bounded worker events separately.

`/api/health` checks web/database reachability. `/api/ready` additionally requires a worker heartbeat within three minutes, each free feed checked within ten minutes, a verified backup within eight hours, and a successful restore drill within 35 days. A stale feed or backup produces 503 so the independent external monitor also detects broken ingestion or recovery readiness while the UI still shows cached games. These routes expose only booleans/status.

Inspect bounded logs with `journalctl -u bayline-backup -n 30` and `docker compose --env-file production.env -f compose.production.yaml logs --tail 50 worker`. Avoid dumping container environments, the secret directory, expanded Compose configuration or the whole Docker inspect object. Verify disk free space before each release and keep at least 10 GB available. Never use `docker compose down --volumes` in normal operations.

Season records require migration 006 and the `record_sync`, `record_games` and `record_poll_gate` tables. Check all six league/phase snapshots have `published_generation` and no `last_error_code`; empty playoff snapshots before playoffs are valid. Initial backfills take several minutes and publish only after the final page. The single worker resumes stored cursors after restart and shares the sports-provider request throttle with scores. Records are marked delayed on error or after six hours without a completed snapshot; this optional feature does not fail score readiness. See [RECORDS.md](../RECORDS.md). After a restore, verify six migrations and published generations/row counts against the backup's release evidence, in addition to the helper's general recovery guards. Dumps include the snapshots and cursors; an absent snapshot can be rebuilt from the free games feed without a paid standings subscription.

Backups retain 35 days. Cleanup deletes only app-shaped object versions under `postgres/` older than 35 days, after at least two completed backups exist. Access is bucket-private and encrypted by Lightsail at rest and in transit. This covers **server loss**, not AWS-account compromise; instance resource access is full bucket access, not an immutable or cross-account backup. AWS credentials/account protection remains essential.

## Recovery from total server loss

Target RPO: at most six hours plus backup execution time. Target RTO: one to two hours after operator access is available. These are targets until timed drills establish measured results. Recovery does not depend on the failed server's disk, Docker volumes or saved ECR login.

1. Refresh AWS SSO, obtain the latest Git release and recorded image digests, and confirm the private backup manifests are accessible. Fence the old server so it cannot resume its worker. Do not delete any source/bucket/repository/static IP while recovering.
2. Update the **existing regional CloudFormation stack** with a new instance suffix, using the current infrastructure template and Ubuntu 24.04 `$24` bundle. Review the change set before executing it. The original source bucket, ECR repositories, budget and backup bucket stay in that stack; do not create a second whole stack with conflicting budget/resource names. A replacement incurs overlapping hourly charges until the old instance is explicitly retired; budget for that short overlap. Retain and reattach the original static IP, and attach the replacement to the retained private backup bucket. A retained old instance is not automatically deleted by CloudFormation.
3. Install Docker/Compose/AWS CLI, deployment files, units and the recorded image digests. Reconfigure secrets through stdin. The database password can be freshly generated; the dump uses `--no-owner --no-acl`. Recover the provider key from the user's original encrypted/secret-manager copy. Never depend on the lost server as the only key copy.
4. Pull the recorded images using a fresh ECR token. Start **only db** on the empty replacement. Run `python3 ops.py restore --no-record --key postgres/EXACT_COMPLETED_MANIFEST.json`. This restores to the isolated timestamped database and verifies its canary/data, without requiring a schema in the newly created live database.
5. Stop all app/worker/migration processes before promotion. Run `python3 ops.py promote --database bayline_restore_TIMESTAMP` using the exact verified timestamped database name. The helper checks that the new `bayline` database has **zero public application tables**, the restored data/canary are present, and no app/worker/migration process is running. It preserves the empty initial database as `bayline_empty_TIMESTAMP`, then promotes the restore by renaming it to `bayline`. It never drops a database and refuses a populated live target. If any guard fails, stop and investigate.
6. Run the image's migrations against the restored live database, start web and exactly one worker, and verify stored schedules, a fresh heartbeat and provider checks. Take a fresh off-server backup and run the isolated restore drill again. Re-enable the timers/watchdog.
7. Reattach the static IP (or update DNS if deliberately changing it), start Caddy, verify trusted HTTPS and readiness, and confirm the external monitor returns OK. Reboot once and recheck services/data/timers. Record elapsed recovery time and the source backup timestamp to establish actual RTO/RPO.
8. Retire only the explicitly identified old instance and obsolete test databases after recovery evidence is reviewed. Do not remove the retained off-server backups or release images needed to recover again.

## Release rollback

Take and verify a backup first. Record current image digests and pin the prior compatible web/worker digests in `production.env`, pull them using a fresh ECR token if absent, and recreate only the relevant services. Do not automatically reverse database migrations. New migrations must remain backward-compatible with the prior app release or have a separately tested restore/promotion plan. Check readiness and monitor state after rollback.
